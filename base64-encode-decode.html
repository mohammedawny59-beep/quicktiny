Standard Base64 vs. URL-safe Base64 (Base64URL)

Standard Base64 uses + and / as its last two alphabet characters and pads the output with =. Those characters have special meaning in URLs and filenames, so a URL-safe variant — Base64URL, defined in RFC 4648 §5 — replaces them with - and _ and typically omits padding. You'll see Base64URL specifically in JWTs (JSON Web Tokens), OAuth tokens, and anywhere a Base64 value needs to sit safely inside a URL or query string. The two are otherwise the same encoding — check the box above to encode as URL-safe, and decoding auto-detects which variant you've pasted.

Python binascii.Error: Incorrect padding

Python — base64.b64decode() / base64.urlsafe_b64decode()binascii.Error: Incorrect padding

Base64 encodes input in groups of 4 characters representing 3 original bytes. When the encoded text doesn't end on a full group of 4, the standard pads it out with one or two trailing = characters. Python's base64 module is strict about this — if padding is missing or wrong, it raises binascii.Error: Incorrect padding instead of guessing what you meant.

This comes up constantly with JWTs and OAuth tokens, because the JWT spec explicitly says to strip padding from each Base64URL segment. A token segment that's perfectly valid by JWT rules will still fail Python's decoder until you add the padding back.

Broken (padding stripped, JWT-style)
eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkFsZXgifQ
Fixed (padded to a multiple of 4)
eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkFsZXgifQ==

In Python, pad the string out to a multiple of 4 before decoding:

import base64

s = "eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkFsZXgifQ"
padded = s + "=" * (-len(s) % 4)
base64.urlsafe_b64decode(padded)
# b'{"sub":"1234567890","name":"Alex"}'

Or skip the math: paste the unpadded string into the tool above and click Decode. QuickTiny detects the variant and adds the missing padding automatically before decoding — entirely in your browser, nothing uploaded — so a string that fails in Python's strict decoder still decodes fine here.

JavaScript atob() / btoa() errors: InvalidCharacterError

JavaScript — atob()InvalidCharacterError: Failed to execute 'atob' on 'Window': The string to be decoded is not correctly encoded.

The browser's native atob() is stricter than it looks — it throws this error on invalid Base64 characters, and it doesn't understand URL-safe Base64 at all: a string using - and _ instead of + and / (like aGVsbG8_d29ybGQ, the URL-safe form of a short encoded string) will fail in atob() even though it's perfectly valid Base64URL. Paste the same string into the tool above instead — it auto-detects standard vs. URL-safe and pads it correctly before decoding, so it works without manually swapping characters first.

JavaScript — btoa()InvalidCharacterError: Failed to execute 'btoa' on 'Window': The string to be encoded contains characters outside of the Latin1 range.

Native btoa() can only encode Latin1 (single-byte) characters — it throws this error the moment your text contains an emoji or a character outside that range (most Western European accented letters, like é or ü, actually fall inside Latin1 and encode fine; it's emoji and less-common scripts that trigger this), since Base64 only knows how to encode bytes, not arbitrary Unicode text directly. QuickTiny's encoder UTF-8 encodes your text first, so any Unicode text encodes correctly instead of throwing this error.

Python binascii.Error: Invalid base64-encoded string (wrong length)

Python — base64.b64decode()binascii.Error: Invalid base64-encoded string: number of data characters (5) cannot be 1 more than a multiple of 4

This is a different problem from the padding error above — it means the string's length itself can't be valid Base64 no matter how much padding you add. Valid Base64 data always comes in groups of 4 characters before padding; a length that's exactly 1 more than a multiple of 4 is mathematically impossible, which usually means a character was accidentally added or dropped — a copy-paste that grabbed one extra character, or two fragments joined together incorrectly.

Unlike a padding problem, this can't be fixed by adding = characters — check the string against its original source for a dropped or duplicated character instead.

Frequently asked questions

Does this support emoji and non-English text?

Yes. Text is UTF-8 encoded before Base64 conversion, so emoji and non-Latin scripts round-trip correctly, in both standard and URL-safe mode.

What's the difference between Base64 and Base64URL?

Only the alphabet for two characters, and padding. Standard Base64 uses + and / with = padding; URL-safe Base64 (Base64URL) uses - and _ instead and usually skips padding, so the result is safe to place directly in a URL. The underlying encoding is identical otherwise.

How does the decoder know which variant I pasted?

It looks for the distinguishing characters: + or / means standard Base64, - or _ means URL-safe. If your string contains neither (just letters, numbers, and padding), it's valid in both forms and decodes identically either way.

What happens if I decode invalid Base64?

You'll see a clear error message instead of garbled output or a silent failure — including when a string mixes standard and URL-safe characters, which isn't valid in either form.

Is Base64 encryption?

No — Base64 is an encoding, not encryption. It's reversible by anyone and shouldn't be used to protect sensitive data.

Why does Python say "Incorrect padding" when this tool decodes the same string fine?

Python's base64 module requires exact padding and raises binascii.Error: Incorrect padding when it's missing — common with JWT segments, which strip padding by design. QuickTiny pads automatically before decoding, so a string that fails in Python decodes here with no extra steps. To fix it in Python, append "=" characters until the string's length is a multiple of 4.

Why does JavaScript's atob() throw "InvalidCharacterError"?

Native atob() rejects invalid Base64 characters and doesn't understand URL-safe Base64 (the - and _ characters) at all. Paste the same string into the tool above instead — it auto-detects the variant and pads it correctly before decoding.

Why does btoa() throw "characters outside of the Latin1 range"?

Native btoa() can only encode single-byte Latin1 characters, so it throws on emoji and less-common scripts — most Western European accented letters (é, ü, ñ) actually fall inside Latin1 and encode fine. QuickTiny UTF-8 encodes your text first, so any Unicode text encodes correctly regardless.

Why does Python say "number of data characters cannot be 1 more than a multiple of 4"?

This means the string's length itself is invalid — a character was likely added or dropped by accident (e.g. during copy-paste), not just missing padding. Unlike the padding error, this can't be fixed by appending "=" — check the string against its original source for a dropped or extra character.
